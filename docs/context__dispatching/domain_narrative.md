## 1. 业务愿景 (Business Vision)

Dispatching（派发上下文）的业务愿景是提供**绝对可靠、非阻塞、且与业务解耦的 Agent 执行环境**。

在与真实的大模型（特别是通过 CLI 工具如 `claude-code` 交互时）打交道的物理世界中，充满了混乱：进程可能挂死、API 会遭遇限流、网络会超时、模型会输出乱码。Dispatching 的存在，就是为了将这些“脏活累活”和“混沌状态”全部拦截在自己的边界内。它向下驯服桀骜不驯的底层 SDK 与子进程，向上为 Orchestration 提供一个极其干净、确定（哪怕是确定的失败）的执行契约。它不问“为什么要做这个任务”，只管“如何把这段提示词安全地送达并把结果完整地带回来”。

## 2. 核心职责边界 (Core Responsibilities & Boundaries)

* **职责所在 (In-Scope):**
    * **指令履约：** 接收来自 Orchestration 的执行契约（包含会话 ID、角色设定、具体指令），并将其原封不动地转化为底层 SDK 可以理解的入参。
    * **生命周期纳管：** 负责唤醒、监控、终止与底层大模型交互的会话进程。这包括处理由于执行时间过长导致的异步等待与状态维持。
    * **混沌隔离（防腐）：** 充当物理防波堤。捕获底层 SDK 抛出的各种奇葩异常（如子进程崩溃、Token 耗尽、网络断开），将其转化为系统内部标准化的“派发失败原因”。
    * **过程透传（可选/未来演进）：** 在长时间的执行过程中，收集底层的标准输出（stdout/stderr），为未来的可观测性（如实时日志流）提供数据源。
* **坚决隔离 (Out-of-Scope):**
    * **业务逻辑与层级：** 坚决不理解什么是“原子层”、什么是“架构层”。它眼中的任务只有“一段带 ID 的文本”。
    * **会话生命周期决策：** 坚决不决定何时该创建新会话、何时该复用旧会话。它完全服从 Orchestration 传来的指令（如果指令说用旧的，就绝不新建）。
    * **任务图谱流转：** 坚决不直接与外部的 `Task Graph` 或 `Event Gateway` 交互。它的唯一上游客户只有 Orchestration。

## 3. 核心业务流程 (Core Workflows / User Stories)

本上下文在 MVP 阶段主要承载以下两个叙事流程：

### 3.1 稳定态：代理执行流 (The Happy Path Execution)
当 Orchestration 下达了一份明确的“派发指令”时，Dispatching 开始工作：
1. **指令接管与翻译：** Dispatching 拿到指令，不看里面的业务内容，只提取关键的“载荷”（如具体的 Prompt）和“目的地”（如 SDK 需要的会话目录或标识）。
2. **异步唤醒：** 它调用底层的 Agent SDK（在当前阶段表现为拉起一个 `claude-code` 的异步子进程）。此时，Dispatching 会极其小心地挂起自己，绝不阻塞主程序的事件循环，让主程序可以继续去监听其他事件。
3. **静默监控：** 在漫长的执行过程中，Dispatching 保持静默监听。它看着底层模型思考、生成、执行工具（如写文件、跑测试）。
4. **结果封装与上报：** 当底层会话自然结束（退出码为 0），Dispatching 收集最终的 Artifacts（如修改的文件列表、执行总结），将其打包成一个标准的“派发成功回执”，交还给 Orchestration。

### 3.2 异常态：防波堤流 (The Breakwater Resilience Flow)
当现实世界发生意外时，Dispatching 必须展现出其作为防波堤的价值：
1. **捕获底层崩溃：** 假设 `claude-code` 进程由于某种原因（如死锁、OOM）非正常退出，或者底层 API 持续报错超时。
2. **强制熔断与清理：** Dispatching 绝不允许这种僵死状态无限期挂起系统。它必须有机制（如超时时钟）主动发觉异常，并对底层的僵尸进程执行“无情抹杀（Kill）”，释放系统资源。
3. **标准化错误转译：** Dispatching 检查崩溃的现场（如 stderr 中的报错信息），将这些晦涩的底层错误，翻译成业务层能听懂的语言（例如：“底层执行引擎崩溃”或“模型响应超时”）。
4. **生成失败回执：** 它将错误信息打包成“派发失败回执”返回给 Orchestration。它自己绝不擅作主张去重试（除非是非常底层的网络抖动重试），因为“是否值得重试”或“重试多少次”是编排大脑（Orchestration）或更上游图谱引擎该决定的事情。

## 4. 关键业务约束 (Business Constraints)

1. **绝对非阻塞 (Absolute Non-Blocking)：**
   Dispatching 的任何外部调用动作（特别是拉起子进程和等待 I/O）**必须且只能**是异步的。它绝不允许发生“为了等一个 Agent 写完代码，整个 `agent-engine` 停止响应其他事件”的灾难。
2. **上下文无知 (Context Ignorance)：**
   Dispatching 在处理任何请求时，不能依赖除了“当前传入的指令”之外的任何外部上下文。它不应该去数据库里查这个任务属于哪个项目，因为这些信息 Orchestration 已经在指令里喂给它了。这就保证了 Dispatching 极其容易被单独抽离、测试或在未来做成微服务。
3. **不遗留脏态 (No Dirty State Behind)：**
   无论一次执行是成功、失败、还是被强制终止，Dispatching 必须保证底层资源（如子进程、文件描述符、本地临时目录）被正确回收。
