## 1. 业务愿景 (Business Vision)

Orchestration（编排上下文）是整个 Agent Engine 的中枢神经。它的核心使命是**将静态的、离散的业务状态流转，转化为动态的、连贯的 AI 协作过程**。

外部的图谱引擎计算着庞大任务的依赖关系与层级结构，但图谱本身是没有“记忆”的。Orchestration 的存在，就是为了给这些任务注入“认知与记忆”。它被动聆听来自外部的号角（事件），精确解析出“现在需要什么角色出场”以及“这个角色应该继承哪一段历史记忆”，然后将完整的行动纲领下发给底层的执行部件。它是一个纯粹的协调者，恪守着“只调度资源、不干涉业务依赖”的底线。

## 2. 核心职责边界 (Core Responsibilities & Boundaries)

* **职责所在 (In-Scope):**
    * **事件响应与动作决断：** 接收来自事件总线的就绪与审查通知，决定唤醒哪种工作流。
    * **角色投射：** 解析外部事件中的层级元数据，向能力注册中心“索要”对应的 AI 角色画像与标准作业指导（提示词）。
    * **认知连续性管理 (会话粘合)：** 负责为每一个特定的“工作坐标”锁定并维护一条连贯的 AI 记忆流（Session）。确保同一个角色在处理同一个维度的任务时，拥有不可割裂的上下文。
    * **组装与派发：** 将“你是谁”、“你要记住什么”以及“你现在要做什么”打包成不可变的执行契约，单向传递给底层的交互派发器。
* **坚决隔离 (Out-of-Scope):**
    * **图谱结构与依赖：** 坚决不维护任务是如何从战略层拆解到代码层的，也不关心任务之间的前置或后置关系。
    * **审查链推导：** 坚决不计算“谁该审查谁”。执行者和审查者的身份标识均完全信任并依赖外部事件的直接指定。
    * **底层通信机制：** 坚决不涉及如何与大模型建立连接、如何处理网络超时或进程挂起。

## 3. 核心业务流程 (Core Workflows / User Stories)

本上下文由以下核心叙事驱动：

### 3.1 监听与生命周期守候 (The Awakening)
在系统启动时，Orchestration 激活其感官，接入全局的事件集线器。它不主动拉取任何任务，而是保持静默，等待着具有明确业务意图的信号（如某个代码块已具备编写条件，或某个架构设计已提交等待审查）打破这种静默。

### 3.2 任务执行编排流 (Execution Workflow)
当系统捕获到一个“任务已就绪”的事件时，Orchestration 会展开以下心智活动：
1. **解析工作坐标：** 从事件中提取出详尽的方位信息。这不仅包括这是哪个项目、哪个根任务，还包括它属于什么结构层级（如上下文层、架构层、原子层），以及该层级下的具体定位（如特定的限界上下文名称、特定的领域模型名称）。
2. **确认扮演角色：** 拿着解析出的“层级身份”，向系统内的角色库询问：“在这个层级下作业，应该采用什么身份与行为规范？”
3. **唤醒历史记忆：** Orchestration 会利用刚刚提取的“工作坐标”去检索是否存在匹配的记忆流（Session）。如果该坐标下已经有过工作痕迹，它会无缝衔接之前的记忆；如果这是一个全新的探索区域，它将开辟并初始化一段新的记忆流。
4. **下达执行指令：** 最后，Orchestration 将任务目标、角色规范和记忆流信标组合在一起，递交给专门负责外呼的派发部门，由其完成实际的劳作。

### 3.3 跨层级审查编排流 (Review Workflow)
当执行部门完成工作并向外部图谱汇报后，外部图谱可能会要求进行质量把控，从而抛出一个“审查请求”事件。Orchestration 对此的响应极其干脆：
1. **提取审查者画像：** Orchestration 直接从事件载荷中读取“谁来审查”的明确指令。它不需要自行推理“由于当前是原子层，所以审查者是架构层”，而是完全遵从事件中指定的审查者层级和具体范围。
2. **确认扮演角色：** 同样地，向角色库索要该审查者应具备的身份与提示词。
3. **唤醒审查者记忆：** Orchestration 根据事件中指定的审查者工作坐标，唤醒那段特定的记忆流。这确保了审查者是带着最初做设计时的“全局视野和历史初衷”来审视当前的产出物，而不是以一个旁观者的身份重新理解项目。
4. **下达审查指令：** 组装审查目标、角色与记忆，派遣给底层执行，并将审查的最终判决（通过或驳回）如实转告给外部图谱引擎。

## 4. 关键业务约束 (Business Constraints)

1. **多维会话绝对唯一性 (Multidimensional Session Singularity)：**
   一个 Agent 记忆流（Session）的存在与复用，必须被一个多维度的联合坐标严格锁定。这个坐标由 **`项目标识` + `根任务标识` + `结构层级` + `具体的范围详情`** 共同组成。
   *这意味着：“负责核心域架构设计的 Agent” 与 “负责支撑域架构设计的 Agent” 即便处于同一层级、同一任务下，也必须拥有完全独立且唯一的记忆流，绝不可相互污染。*
2. **事件作为唯一真相源 (Event as the Single Source of Truth)：**
   无论是执行还是审查，Orchestration 所需的所有前置决策依据必须100%来源于外部事件的载荷。如果事件信息不足以锁定工作坐标或角色身份，流程必须中断并抛弃，绝不允许在 Orchestration 内部进行任何形式的默认值推测或关系推理。
